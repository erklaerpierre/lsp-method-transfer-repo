# Bauaufgaben (Challenge Questions) formulieren

Die Bauaufgabe entscheidet, ob ein Workshop Tiefe bekommt. Sie muss zum Zweck passen, offen sein und im Bauen eine Metapher möglich machen.

## Regeln

1. **Offene Frage statt Anweisung.** Das Modell ist die Antwort. Die Frage darf mehrere Wege zulassen.
2. **Metapher einladen.** Vermeide Formulierungen, die nach einem Diagramm klingen ("Zeichne", "Stelle dar", "Erstelle eine Übersicht"). Besser: "Baue, wie sich … anfühlt", "Baue ein Modell, das zeigt …".
3. **Ein Gedanke pro Frage.** Wenn zwei Themen nötig sind, zwei Aufgaben stellen.
4. **Bauzeit nennen.** Typisch 3 bis 5 Minuten für Mikro-Builds, 5 bis 10 für Standard, 10 bis 20 für komplexe Modelle. Zeit sichtbar halten.
5. **Zum Stand der Gruppe passen.** Zu schwer führt zu Angst, zu leicht zu Langeweile (Flow).
6. **Erst individuell.** Jede Aufgabe wird zuerst von allen einzeln gebaut.
7. **Teilen mit einplanen.** Pro Modell etwa 1 bis 3 Minuten, bei sechs Personen also rund 6 bis 18 Minuten pro Zyklus.
8. **Keine Bewertungsfrage.** Nicht: "Baue die beste Lösung". Besser: "Baue eine Lösung, die für deinen Alltag einen Unterschied macht."
9. **Zum Thema des Workshops zurückführen.** Warm-ups sind abstrakt, die Kernaufgaben konkret.

## Muster

| Ziel | Muster | Beispiel |
|---|---|---|
| Ist-Zustand verstehen | "Baue, wie du … heute erlebst." | "Baue, wie du die Zusammenarbeit in unserem Team heute erlebst." |
| Gefühl und Wirkung | "Baue die Situation, in der … und zeige, was dabei in dir vorgeht." | "Baue den Moment im Onboarding, in dem Kunden aussteigen, und zeige, was sie dabei fühlen." |
| Hindernis | "Baue, was dich daran hindert, …" | "Baue, was uns bremst, schneller zu liefern." |
| Idee | "Baue eine Lösung, die …" | "Baue eine Lösung, die das Problem aus Sicht der Nutzerin spürbar entlastet." |
| Mutig | "Baue eine Idee, die verrückt wirkt, aber das Problem lösen würde." | |
| Rolle und Perspektive | "Baue, wie [Rolle] die Situation erlebt: Ziel, Sorge, Handlungsspielraum." | |
| Verbindung | "Verbinde dein Modell mit einem anderen und baue die Verbindung so, dass man ihre Art erkennt." | |
| Kriterium | "Baue das Kriterium, nach dem wir heute entscheiden sollten." | |
| Nächster Schritt | "Baue den kleinsten Schritt, der die Idee real macht." | |
| Erfolgssignal | "Baue, woran wir in zwei Wochen erkennen, dass wir vorankommen." | |
| Zukunft | "Baue das Bild, das wir in zwölf Monaten sehen wollen." | |
| Leitprinzip | "Formuliere aus dem, was du im System siehst, eine einfache Regel für Entscheidungen." | |
| Emergenz | "Ein unerwartetes Ereignis tritt ein: [Ereignis]. Baue, was im System passiert." | |

## Warm-up-Aufgaben (Skill Building)

Kurz, ohne Bezug zum Workshopthema. Reihenfolge von einfach zu bedeutungsvoll:

1. "Baue einen möglichst hohen Turm in 2 bis 3 Minuten." Danach jede Person sagt einen Satz dazu.
2. "Baue eine Kreatur." Danach: "Mache daraus in 4 Minuten eine Metapher für [harmloses Thema, z. B. idealer Urlaubstag]."
3. "Baue deinen Montagmorgen." Erste vollständige Geschichte.
4. Optional: "Baue eine Metapher für dein Verhältnis zu [Thema des Workshops]."

Vermeide für Einsteiger heikle Themen im Warm-up (Chefs, Konflikte), es sei denn, der Rahmen ist sicher.

## Folgefragen im Teilen

Fragen über Modell und Geschichte, nicht über die Person:

- "Erzähl mehr über dieses Element."
- "Was bedeutet [Farbe/Stein/Position] in deinem Modell?"
- "Welche Beziehung besteht zwischen diesen beiden Teilen?"
- "Was fehlt in deinem Modell, was würdest du gern ergänzen?"
- "Was daran ist dir besonders wichtig?"

Vermeide: "Warum hast du das gebaut?", "Meinst du damit …?", "Gute Idee."

## Warum-Fragen umwandeln

Warum-Fragen verlangen von der Person, ihre Absicht zu rechtfertigen. Wandle sie in Fragen um, die auf Bedeutung, Erleben oder Struktur im Modell zielen, und hänge `[Umformuliert]` an. Nenne in der Kompatibilitätstabelle die Original-Frage.

| Original (Warum-Frage) | Umformuliert | Kennzeichnung |
|---|---|---|
| „Warum hast du das so gebaut?“ | „Was bedeutet dieses Element in deinem Modell?“ | `[Umformuliert]` |
| „Warum ist das ein Problem?“ | „Wo im Modell zeigt sich das Problem, und wie sieht es dort aus?“ | `[Umformuliert]` |
| „Warum war das frustrierend?“ | „Erzähl, wie sich diese Situation in deinem Modell zeigt.“ | `[Umformuliert]` |
| „Warum ist dieser Stakeholder relevant?“ | „Welche Rolle spielt dieser Stakeholder in deinem Modell, und was zeigt seine Position?“ | `[Umformuliert]` |
| „Warum ist diese Verbindung kritisch?“ | „Was bedeutet diese Verbindung für das System, und was geschieht, wenn sie reißt?“ | `[Umformuliert]` |
| „Warum genau wirkt diese Veränderung?“ | „Was verändert sich im Modell durch diese Veränderung?“ | `[Umformuliert]` |
| „Warum?“ vor „Wie?“ (Bedeutung vor Funktion) | „Was bedeutet das für dich?“, danach „Wie zeigt sich das?“ | `[Umformuliert]` |
| 5 Whys (Ursachenkette) | „Was steht hinter diesem Element?“, wiederholt bis zur Wurzel, jede Antwort als Anbau am Modell | `[Umformuliert]` `[Zu testen]` |

Ausnahme: Das Wort „Warum“ im Sinn von „Zweck des Projekts“ (z. B. „das Warum des Projekts“) ist kein Frageproblem. Es bleibt, wenn es keine Person zur Rechtfertigung auffordert.

## Prüfliste pro Bauaufgabe

- [ ] offen formuliert, nicht als Anweisung für ein Diagramm
- [ ] Metapher oder Geschichte möglich
- [ ] eine zentrale Idee
- [ ] Bauzeit genannt
- [ ] vom Einzelmodell aus gedacht
- [ ] Teilen und Reflexion eingeplant
- [ ] Sprache ohne Bewertung
